How "#1" is decided

Overall ranking — and the exact formula behind it

An opinionated but explicit weighting for a local agentic-coding driver in OpenCode — using the q4 quant unless noted, decode normalized to the fleet max of 137 t/s.

Overall = 0.35·A_coding + 0.25·(1 − tool_malformed%) + 0.15·C_edit + 0.10·B_recall + 0.10·(D_text/10) + 0.05·(decode/137) → ×100
A_coding 35% — writes correct code Tools 25% — drives tools reliably C_edit 15% — surgical-edit precision B_recall 10% — planted-bug review D_text 10% — prose / communication Decode 5% — speed, tiebreaker only

Why these weights: for an agentic coding driver the two things that matter most are does it write correct code (A, 35%) and does it reliably drive tools without malformed calls (tools, 25%); surgical-edit precision (C, 15%) is next; planted-bug review (B, 10%) and prose (D, 10%) are secondary; raw speed (5%) is a tiebreaker — all models are usable except the noted slow one. RAM is a constraint, not scored.

What each column measures

Metric glossary

A_coding

pass_rate, 0–1. Suite A: the model implements a coding task in an OpenCode session; score = fraction of a hidden pytest suite that passes. 5 tasks × reps. Higher = writes more correct code.

C_edit

pass_rate + surgical_score. Suite C: apply a surgical edit to existing code — fix the target without touching unrelated lines. A separate surgical_score measures diff minimality and whether planted "noise" edit-requests were correctly ignored.

B_review

recall / precision. Suite B: review code with planted bugs and report them. Recall = fraction found; precision = fraction of reports that were real. The fleet-wide weakness — recall spans 0.11–0.56.

D_text

0–10, LLM-judged. Suite D: free-text tasks (summarize a doc; de-duplicate approaches), judged 0–10 by an offline Opus judge against a fixed rubric. 3 reps each × 2 tasks.

Tools malformed

%. Share of tool-calls that were malformed (bad JSON / wrong schema) and had to be retried. The reliability axis for agentic use — a high number means a working model that still wastes turns.

Decode t/s

Tokens/sec generation speed from a dedicated speed probe (warm). Separate from prefill (time-to-first-token), which is cold-dominated.

RAM GB

Peak unified-memory footprint on the 36 GB Mac. A constraint, not a quality score.

Termination taxonomy

clean finished the task · no_tools emitted prose and stopped without ever calling a tool · hit_timeout ran into the 900 s wall.

How the experiment was run

Methodology

Machine
One MacBook Pro, Apple M4 Max, 36 GB unified memory, 32-core GPU (Metal 4). Nothing leaves the laptop — fully local inference.
Serving
Each model served locally by llama.cpp llama-server (via unsloth-serve) on 127.0.0.1:8888, one model in RAM at a time, strictly serial. Quants are GGUF (q4/q5/iq4/mxfp4 as noted).
Driver
Models drive OpenCode headless (opencode run … --agent build) as real agentic coding sessions — the same harness used daily, not a synthetic prompt.
Unit of measurement
One (model, quant, suite, task, rep). Idempotent per-unit results on disk; 450 units across 9 working models.
Suites
A_coding (correctness), B_review (planted-bug recall/precision), C_edit (surgical edits), D_text (free-text, judge-scored). 3 reps per text task.
Quants tested
Most models at q4 and q5; single-quant for qwopus (q5), ornith (q4), gpt-oss (mxfp4); katdev at q4 + iq4. Finding: Q4 ≥ Q5 on coding across the board.

Two quirks disclosed for honesty

  • (a) MTP speculative-decode acceptance rate was never captured — the probe didn't record it.
  • (b) Three of the models were driven with a deterministic 12.7 K base prompt (all MCP tools stripped) vs. 15.8–18.8 K for the other six — that delta is tool schemas the tasks never call, so it doesn't move the quality metrics; speed comparability rides the separate raw-endpoint probe.
