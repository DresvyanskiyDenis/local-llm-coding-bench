The document explains how LLM inference splits into two phases: **prefill** (compute-bound, processing the entire prompt in parallel to produce the first token) and **decode** (memory-bandwidth-bound, generating one token per pass over the model's weights). Because decode reads all weights and KV cache for each output token but does minimal computation per byte, it's extremely inefficient.

The KV cache — storing key/value projections for every token — avoids recomputing attention at each step, but grows linearly with context length and competes with model weights for memory, especially on unified-memory machines like Apple Silicon where RAM is shared with the OS and other applications.

**Speculative decoding** tackles decode's inefficiency by having a cheap mechanism propose several candidate tokens (a "draft"), then verifying all of them in a single forward pass — the same memory traffic as one token but scored against multiple candidates simultaneously. If accepted, those tokens are free; if rejected, the model falls back to its own prediction from that point. **Multi-Token Prediction (MTP)** is a variant that attaches small extra prediction heads directly to the base model, avoiding the need for a separate draft model and its additional memory footprint.

The **acceptance rate** — the fraction of drafted tokens the verifier accepts — determines actual speedup. It varies by workload: code generation sees higher rates than free-form prose due to its structure. Hardware matters too: GPUs with high compute-to-bandwidth ratios (CUDA cards) see dramatic speedups from speculative decoding, while Apple Silicon's unified memory and different balance means the same acceptance rate doesn't automatically yield the same gains. The practical takeaway is that MTP and speculative decoding only help if measured acceptance rates on your specific hardware, model, and quantization level are high enough to offset the extra computation.
